# AI-native SDLC, the way we work here

One **cycle** = one small outcome, taken through six stages. Every stage leaves a file in `cycles/NNN-name/`, so the next session (or agent) starts from the files, not from the chat.

```
intent → spec → plan → build → verify → learn
  ▲                                       │
  └───────────── next cycle ◄─────────────┘
```

| # | Stage | File | Question it answers | Human gate |
|---|-------|------|---------------------|------------|
| 1 | **Intent** | `intent.md` | Why, for whom, what does "done" look like, what are we NOT doing? | You confirm the goal and success measure |
| 2 | **Spec** | `spec.md` | What exactly will be true when finished? (acceptance criteria, constraints, out of scope) | You approve the spec |
| 3 | **Plan** | `plan.md` | In what thin slices, in what order, touching which files, with which checks? | You approve the slices |
| 4 | **Build** | commits + the plan's "As run" log | One slice at a time | Per-slice check |
| 5 | **Verify** | `verify.md` | Evidence for each acceptance criterion | You accept or send back |
| 6 | **Learn** | `learn.md` | What changed in our understanding, docs, memory, rules? | You pick what becomes permanent |

## Rules

1. **Intent is interrogated, not dictated.** The agent grills (one question at a time, with a recommended answer) until the open questions in `intent.md` are closed or explicitly parked.
2. **No code before the spec is approved.** Throwaway spikes are fine, labelled as spikes and never merged as the answer.
3. **Slices are small enough to verify alone.** Each slice has its own check and rollback.
4. **Evidence over assertion.** `verify.md` points at output, numbers or a drill result, not "it works".
5. **Decisions are written down** in the cycle's `decisions.md` with the reason, so they are not re-argued.
6. **Learn feeds back.** Durable findings go to the project's docs, memory or rules, and the cycle ends with a list of what moved where.

## Where things live

```
docs/sdlc/
├── README.md        this file: the method and the status table
├── PROJECT.md       this project's profile: how to run things, secrets, board link
├── BOARD.md         generated: the board as a table (do not edit by hand)
├── templates/       one per stage; copied when a cycle reaches that stage
└── cycles/NNN-short-name/
    intent.md  spec.md  plan.md  verify.md  learn.md  next.md  decisions.md  evidence/
```

## The board and "what next?"

- **State comes from the files.** The skill's `scripts/sdlc_status.py` reads every `cycles/*/` folder: a stage's file and the ticked boxes in its gate say whether the stage is done. Nothing is typed in twice.
- **"What next?" comes from `next.md`** in each cycle: one line per action, `- [ ] [owner|claude|both] <date, optional> text`.
- **`BOARD.md`** is regenerated by the script after every step that moves a cycle. If `PROJECT.md` names a live board (an artifact), it is refreshed too.

## Importance and dismissed cycles

- **Importance (1 to 5)** ranks the cycles, in the header table of each `intent.md`: `| **Importance** | 4/5 (claude, YYYY-MM-DD): reason |`. 5 critical, 4 high, 3 useful, 2 minor, 1 marginal. The agent assesses it first; the owner overrules it with `(owner, date)`.
- **Dismissed** is a decision, not a deletion: the intent gets `| **Status** | Dismissed YYYY-MM-DD by the owner: reason |`, its `next.md` is ticked, and the folder stays as the record.
