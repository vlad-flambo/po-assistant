# Decisions: cut the runner's reads from Neon

One entry per decision, newest last. Do not edit old entries: add a new one that supersedes.

## D1. A local working copy with a push-up (the intent's B and C) is deferred; reduce the specific reads first
- **Date:** 2026-10-29
- **Context:** The intent shortlisted an on-demand local copy that the runner works on (B), refreshed incrementally (C). A read-only map of the code showed that the runner and the web app both write most of the tables that matter (`Job`, `CandidateJob`, `Score`, `StatusChange`, `Candidate`, `Config`, `Source`, `AiTask`), that keys are auto-increment ids that appear in agent files and e-mail links, that there is no `updated_at` to pull changes by, that deletions cascade widely, and that no router or incremental copy code exists. The runner already overwrites a user's triage in a window of milliseconds; on a stale copy the window is a whole run.
- **Options considered:** B/C as written; a read-only copy for reads only with writes straight to Neon (misses jobs the run just ingested); reduce the specific heavy reads in code (a dump, an unused JSON column, full job texts loaded where only a rank is needed) and cache the one heavy column; upgrade the Neon plan; do nothing new.
- **Decision:** Measure first on a scratch copy. Reduce the named reads in order R1 (backup profile), R2 (defer what is unused), R3 (a read-through cache of job texts), each only as far as needed to get the projection under 2.5 GB a month with a 20 % margin. Keep the full working copy (R4) as a last resort with its own cycle.
- **Why:** The reductions touch only what is read, never what is written, so they cannot make the overwrite windows worse; each can be measured before and after on a copy; none needs a sync protocol. The measurement may show that none is needed.
- **Consequences:** The intent's approved shortlist is revised; the owner confirms this by approving the spec. The overwrite windows are recorded as a finding for a possible later cycle.

## D2. Everything is measured on a local scratch copy; nothing touches Neon or sends e-mail
- **Date:** 2026-10-29
- **Context:** Neon's allowance is the scarce resource; the scratch copy holds real candidate data; `pc_runner.ps1` and `saxobeat-runner.cmd` use the hosted address whenever `.env` has one; `mail send` would send for real if a mail provider is configured.
- **Decision:** A dedicated measurement script, `scripts/measure_reads.ps1`, restores the 29 Oct dump into a scratch database, refuses to run unless the target is localhost, removes the hosted address and mail settings from its process, and points the AI and cache folders at scratch folders. The runner scripts are never used for measurement.
- **Why:** Cycle 002's rehearsal showed that a local restore costs nothing on Neon and catches mistakes; the guards remove the two ways a measurement could do real harm.
- **Consequences:** The bytes are what the database container sends (the wire protocol's size, which is what Neon would count as outbound traffic, with small differences).

## D3. R1 is selected: the full backup is monthly (every 30 days), the last 6 kept
- **Date:** 2026-10-29
- **Context:** The owner's pattern is 3 to 5 runner runs a week. A full backup reads 227 MB from Neon (measured), so a weekly one is 908 MB a month on its own: it does not fit under 2,000 MB at any run rate. A smaller dump is not available: leaving out `jobs_job` would break the foreign keys of the candidates' own triage (`jobs_candidatejob`), and the job texts are most of the database.
- **Options considered:** weekly (the existing rule); every two weeks (454 MB a month); monthly (227 MB a month); a partial dump.
- **Decision:** Monthly, as the owner chose: `pc_runner.ps1` now calls `backup_database --min-age-hours 720 --keep 6`. The dump itself is unchanged, so the restore drill already done (slice 2) still holds. Worst case a disaster costs up to a month of work, apart from Neon's own short history and the old project `saxobeat-fallback1` (a snapshot of 2026-10-29).
- **Why:** It is the largest single line of the projection and it needs no change to what is dumped.
- **Consequences:** R2 and R3 (D4) still wait for the web app's own rate. Cycle 004's spec expects a weekly backup file on the PC: that text needs updating (noted in next.md). A manual backup resets the 30-day clock, because the gate looks at the newest local file.

## D4. R2 is selected in parts, R3 is not (PROPOSED 2026-10-29, never confirmed: SUPERSEDED the same night by D5)
- **Date:** 2026-10-29
- **Context:** The profile ([source_pass_profile.md](evidence/source_pass_profile.md)) found where a source pass's reads go: the link lookup (the largest part of a source's own reads, 69 %), the corpus word counts (17.1 MB once a week, a smaller increment each run) and the same candidates and configs read again for every source. A due digest costs 0.1 MB, so the 129 MB guess for digests is dropped. The projection ([projection.md](evidence/projection.md)): at 5 runs a week the runner alone is 2,315 MB with no reduction, 1,952 with R2a, 1,402 with R2a and R2b, before `W`.
- **Options considered:** R2a (slim link lookup); R2b (`ai sync` and digests do not load the job texts they only rank); R2c (recount the corpus every 30 days, not 7); R2d (candidates and configs once per run); R3 (a text cache); R4 (a full local working copy, D1).
- **Decision (proposed):** Build **R2a** now (done, measured, tested, one commit to revert). Build **R2b** next, measured by slice 7b. **R2c and R2d only if `W` leaves too little room** after R2a and R2b. **R3 is not built**: the savings come from not loading the texts, not from caching them. R4 stays parked (D1).
- **Why:** R2a and R2b change only what is read, never what is written; each is measured before and after on the same scratch copy; at 5 runs a week R2a alone leaves 48 MB for the web app, so R2b is needed there, and at 3 runs a week it adds margin. R2c and R2d are small and can wait for `W`.
- **Consequences:** R2a changes how `ingest` loads a job: two links of one source to the same job, one changed and one reopened in the same batch, now lose less of the change than before (4 jobs in a replay of 5,339 postings, made dense on purpose); the real fix (handle a job once per batch) is a finding for a runner-correctness cycle, not made here.

## D5. Keep two small, measured reductions; build nothing more until `W` is read (CONFIRMED by the owner 2026-10-30)
- **Date:** 2026-10-29 (night)
- **Context:** Two measurements overturned the draft's inputs ([source_pass_profile.md](evidence/source_pass_profile.md), [projection.md](evidence/projection.md)): `ai sync` costs 0.1 MB in steady state (the 32.2 MB was a cold-cache first run), a due digest costs 0.1 MB (not 129 MB a month), and a run is about 63 MB, not 94.9. With the monthly backup (D3) the runner is about **1,045 to 1,611 MB a month** with no reduction, about **830 to 1,248** with R2a, at 3 to 5 runs a week, before `W`. The profile also found that a standard-mode inbox page read the whole ranking pool with job texts: 1.1 MB a page view.
- **Options considered:** build R2a only; R2a and the inbox fix (R2b); also R2c/R2d (corpus every 30 days, candidates and configs once per run); R3; R4 (D1).
- **Decision (proposed):** Keep **R2a** (the slim link lookup) and **R2b** (the ranking pool no longer loads job texts): both are built, measured, covered by a test that fails on the old code, and the suite passes (1,249 tests). **Do not build R2c, R2d, R3 or R4**: at these numbers they are not needed; `W` is the only open input, and the rest wait for it. If `W` plus the runner would exceed 2,000 MB a month, the next moves are, in this order: R2d, then R2c, then a look at the sources' refresh intervals.
- **Why:** The two kept changes only change what is read, never what is written; each was measured before and after on the same scratch copy; each is one small diff that can be reverted. Everything else would add code to solve a problem the projection says is not there.
- **Consequences:** R2a changes how `ingest` loads a job: two links of one source to the same job, one changed and one reopened in the same batch, now lose less of the change than before (4 jobs of 31,968 in a replay of 5,339 postings, dense on purpose); the real fix (handle a job once per batch) is a finding for a runner-correctness cycle. The runner scripts are unchanged by D5. The owner reviews both diffs and says "commit it".

## D6. The runner restarts by hand on prod1, with one measured first run (PROPOSED 2026-10-30; the owner starts it, which confirms it)
- **Date:** 2026-10-30
- **Context:** The standing rule ("no runner, `ai sync` or backup against the hosted database until the plan says how") existed to keep the baseline clean and to avoid a second cap. Now every runner step is measured, the two read reductions are live (Render deployed `8acf7f8`), D5 is confirmed, and the runner plus the monthly backup is about 830 to 1,250 MB a month against a 5,000 MB allowance on a project that has used about 135 MB. The owner asked to restart the runners as soon as possible.
- **Options considered:** wait seven days of readings first; restart now with a measured first run; schedule it again.
- **Decision (proposed):** Restart **by hand now**, following [evidence/restart_runbook.md](evidence/restart_runbook.md): one run with Neon readings before and after, stop rules (an error, more than 0.20 GB for one run, any e-mail), then 3 to 5 runs a week. **Do not schedule it** (Task Scheduler) until a week of readings agrees with the projection. The standing rule is lifted by this decision, for the runner as written in the runbook; a backup of prod1 stays optional and manual.
- **Why:** The allowance is a cap per project and the projected use is a fraction of it; waiting a week would only delay the data, and the first run is itself the most useful measurement left (criterion 9). Two cheap guards stay: the stop rules and the unscheduled runner.
- **Consequences:** The runner writes into prod1 again (ordinary postings and scores; the overwrite windows were closed in cycle 014). `mail send` only queues, because no mail provider is configured (cycle 003). The first run counts the word-count sample in full once (about 17 MB).
