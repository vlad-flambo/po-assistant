## The filter hung the host
A script of mine fetched `/`, `/?reapplied=hide`, `/?min_score=0` and `/?min_score=0&reapplied=hide` one after the other. It timed out after 45 s with nothing returned. A moment later the host showed "Réveil en cours…" (the free server waking up), then HTTP 502 ("service currently unavailable"), then it was back some minutes later. I cannot prove from here that my two filter requests caused the outage (Render's logs would say), but they are the likely cause: the filter query was the only thing that had not been run at the host's size, and on the local copy it reproduces.

**Reproduction** (local Postgres copy of 22 Oct: 57,643 views, 28,800 to 28,843 per candidate; `statement_timeout` 20 s; read only; `explain3.py` and `explain4.py` in the scratchpad):

| Query (candidate 1, status New, 23,977 views) | Correlated `EXISTS` (as committed) | Two small steps (the fix) |
|---|---|---|
| count with the filter | **over 20 s, cancelled** | 0.039 s |
| top 30 by score with the filter | **over 20 s, cancelled** | 0.024 s |
| count without the filter | 0.011 s | 0.011 s |

Candidate 3 (25,940 views): 0.010 s and 0.016 s with the fix. A first `EXPLAIN` of the paged query without the count looked fine (0.18 s), which is why the first check missed it: the slow part is the count and the sort, which must read every row.

**Why the tests did not see it:** they use a handful of rows. The `EXISTS` compared `COALESCE(repost_of_id, job_id)` of two views of the same candidate, an expression no index serves, so each of the 24,000 rows scanned the candidate's 29,000 views.
