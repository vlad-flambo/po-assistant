# What one new account costs (criterion 16), measured 2026-11-06

**Setup.** The 29 Oct 2026 dump (`data/backups/saxobeat_2026-10-29_100546.dump`: 2 candidates, 31,968 jobs, 61,393 job views) restored into the scratch database `scratch033` of the local Docker Postgres, migrated to the current code (0043), then `cost_of_one_account.py 3`: three fresh candidates signed up the way `/join/` does (`accounts.sign_up`), each followed by `matching.backfill` (what the web server starts in a background thread at a new person's first request). Nothing was read from or written to Neon. Raw output: `cost-output-2026-11-06.txt`.

| One new account | Measured (three runs) |
|---|---|
| Job views made (`jobs_candidatejob`) | 30,675 each (of 31,968 jobs) |
| Scores made (`jobs_score`) | 4,348 each |
| Size added, tables and indexes | 8.33, 7.83, 7.87 MB (about **8 MB**); 6.5 to 7.3 MB of it is the job views |
| Time of the sign-up itself | 0.5 s |
| Time of the first backfill | 52.9 to 58.7 s |
| Other rows | one each: user, candidate, config, invitation |

**Reading.**
- An account costs about **8 MB** on this catalogue (30,000 views), not "thousands of rows": ten times more than the spec's D1 text assumed. The brake of the spec (3 per address and 20 in all per hour) still holds as a brake, but 20 accounts in an hour would be about **160 MB**. Against Neon's free 0.5 GB storage that is a third of the project, whatever the number the owner's last reading showed (0.55 GB across projects on 2026-11-05, owner's dashboard; the project's own figure is on its Overview page, not read here).
- The dump predates the 30-day age limit's purge on the host (cycle 031), so today's host catalogue, and with it the cost of an account, may be smaller. The host's job count is not read here (a read on the host is the owner's to allow); `scripts/db_counts.py` gives it without exposing an address.
- Where the time goes: the first backfill takes about a minute of CPU on the web server's one worker (a background thread). Under a flood the single lock lets one backfill run at a time; the others' jobs are made on demand.
- Not measured: the welcome e-mail (Brevo: 300 a day, one per account), and the Neon read transfer of a backfill (it reads job ids and fields, not job texts: `defer("description_text")`).

**What changes in the plan.** Nothing in the slices. The constants (`SIGNUPS_PER_ADDRESS=3`, `SIGNUPS_IN_ALL=20`) stay as approved; the verdict on whether 20 an hour is too loose for a 0.5 GB project goes to the owner with the deploy (one constant to change).
