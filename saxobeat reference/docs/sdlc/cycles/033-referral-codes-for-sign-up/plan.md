## Order and dependencies
- **Measure first (1)**, because D1's numbers and "how many accounts Neon can hold" are guesses until a real new account is counted; if one account turns out to be much bigger or smaller than assumed, D1 is re-opened with the owner before any code.
- **Data (2) before logic (3)**, and logic before any page, so every page is a thin layer over tested functions. Slice 3 changes `sign_up`, so it carries the guard that `tests/test_accounts.py` passes untouched.
- **Sign-up screen (4) before the console (5)**, so a code made in the console can already be used; the console before the candidate's page (6), because the friends count and "came through Marie's code" need both.
- **Delete (7)** needs the table from 2 and the origin link from 3; the guard test in `test_account_delete.py` fails as soon as slice 2 lands until slice 7 lists the table, so slices 2 to 7 are one working-tree stretch: run that file at the end of slice 2 and expect that one failure, named.
- **Looking (8)** needs 4 to 6; **Verify (9)** needs everything; **ship (10)** needs the owner's agreement to commit and push and is last because it is the only step on the host.
- Migration number: the other cycles' intents (025 to 029) are drafts with no migration written, so `0044` is free today; check again at slice 2.

## Rollback
- **Slices 1 to 9:** all in the working tree before any commit: `git checkout -- <paths>` for the changed files, delete the new files, and delete the scratch databases. The migration is only run on scratch copies. Nothing hosted is touched.
- **Slice 10, the code:** `git revert` of the one commit and a redeploy: the sign-up screen and pages disappear, the login page returns to "Accounts are by invitation". The migration is additive (one table, three nullable or blank fields), so leaving it in place is harmless; to remove it, `manage.py migrate jobs 0043` on the host (owner's step, only if wanted), which drops the code table and the origin fields and loses nothing else.
- **A code or sign-up problem on the host:** the owner switches the code off on *People* (no deploy needed) and sign-ups through it stop at once.

## Risks
- **A flood through a known code** (D1): the brakes are the answer; slice 1 measures what a flood would cost. The overall brake means a flood can also stop honest sign-ups for an hour: accepted.
- **Proxy addresses:** the per-address limits trust the first `X-Forwarded-For` entry, as the login throttle does (best effort; the overall brake does not depend on it).
- **Reusing `FailedLogin` rows** for sign-up counts: the model is named for logins. The reserved names `signup-code` and `signup-ok` are constants with a comment; the table is already swept after two days. If this ever reads badly, a rename is one migration.
- **French catalogue and `.mo`** carry other cycles' uncommitted edits: the commit must not sweep them in unannounced.
- **Two writes in parallel:** the first visit to `invite/` twice at once, and two sign-ups on the last place under a brake: handled by the unique constraint (retry on `IntegrityError`) and by counting inside the sign-up transaction; each has a test.
- **The backfill on every new account** is a background thread guarded by one lock; under a flood the second account's jobs are made on demand rather than at once. Not changed here; slice 1's number says whether it matters.
- **The hidden coupling:** the delete's raw `DELETE` skips Django's set-null, so slice 7 must null `origin_code` itself; the test for a friend after the delete is the proof.
