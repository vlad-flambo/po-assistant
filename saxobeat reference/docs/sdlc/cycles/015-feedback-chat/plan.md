## Order and dependencies
- 1 first, because a baseline taken after the change proves nothing.
- 2 before 3 (the endpoints need the model and the script); 3 before 4 (the button is the last thing that exposes the feature, and until then nothing visible changes even if the code were deployed by accident).
- 5 after 3 (it reads the same rows) and can be built before or after 4; kept after so the person's side is finished first.
- 6 after 5 so the strings are final; 7 is independent but placed after the data is final.
- 8 gathers everything before anything leaves this machine; the owner's OK there is the gate for 9.
- 9 is the only step that cannot be undone by simply stopping: once the migration ran on the hosted database the table exists (empty and harmless). 10 and 11 follow it.
- **Shared files:** other sessions are working in this repository today (cycles 004, 014 and others). The plan edits shared files (`base.html`, `urls.py`, `app.css`, `ui.js`, `ops/base.html`, `models.py`, the French catalogue). Before each slice I run `git status` on those paths; if another session has uncommitted edits in the same file I stop and say so, and I commit only the paths this cycle changed (`git add <paths>`), never with `-A`. The migration number is read again at slice 2 and at slice 9 because another cycle may have taken 0041.

## Rollback
- **Slices 1 to 8**: nothing has left this machine; revert the commits (or do not commit).
- **Slice 4 only** (hide the feature without touching data): remove the button and the sheet from `base.html`; the endpoints stay unreachable by any link.
- **Slice 9**: revert the commit and redeploy; the button disappears at once. The empty `feedback` table can stay (additive); if the owner wants it gone, a reverse migration drops it. No existing table is altered, so there is no data to restore. The old Neon project is still the fallback of cycle 002 for the whole-database case.
- **Slice 11**: nothing to undo; items can be deleted from the console or by the person with the account.

## Risks
- **The button shows to every friend the moment slice 9 lands.** That is the intent, but if the owner wants a quiet test first they say so before slice 9, and the plan adds a one-line operator-only switch for a day (rejected so far to avoid a new setting).
- **Overlap with the phone's bottom bars** (tab bar, job action bar, settings save bar, toasts): the likeliest defect; slice 4's screenshots and the owner's phone check are the proof.
- **Query count regression on every page**: slice 4's comparison with slice 1's numbers catches it; the button markup uses no query by design.
- **Shared-file collisions with other sessions** (above) and **a migration-number clash**.
- **A hosted deploy at the same time as cycle 004's checks** (Render's migration log): the owner picks the moment; I do not push.
- **Free text is personal.** Mitigated by cascade deletion, no outside service, and the console being the operator's only view; the slice 7 backup decision means the text is also in database dumps, as every other table is.

**Slice 7, export and backups (2026-10-30).**
- **Decision:** a person's feedback is their own words tied to their account, so it goes in **their own data export** (`/data/export/`, `backup.export_data`) and **comes back with a restore**; the owner's notes on it (the state, the cycle it became) do not (they are not the person's to take, and a file's copy is ignored on restore). The full database backups (`pg_dump`, and the SQLite to Postgres copy, which reads every model of the app) already carry the new table with no change.
- **Code** (`jobs/services/backup.py`, 42 lines): `feedback` list and a count in the export; `_import_feedback` on restore. *Replace* empties the person's chats and puts the file's back (their `created_at` kept); *merge* adds only a chat with a kind and moment not there yet, so twice changes nothing; a chat of an unknown kind, with answers that are not an object, or too large (40,000 bytes of JSON) is skipped with a warning; at most 1,000 chats are read from one file. **A file that has no `feedback` key (made before the chat) does not touch a person's chats, even in replace mode**, so an old backup cannot wipe what they told us since. The schema stays `v1` (the key is additive and an older version ignores it).
- **Tests:** `tests/test_feedback_backup.py` (9) and the existing `tests/test_backup.py` (42) pass: only their own chats and no owner notes in the export, valid compressed JSON, replace and merge, an old file, unreadable and oversized entries, the 1,000 cap, and the download button.
