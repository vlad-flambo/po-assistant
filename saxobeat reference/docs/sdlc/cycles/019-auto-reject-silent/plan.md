## Notes from the build
- **Slice 3:** the first read of the delay creates the one settings row (`get_or_create`, a tiny INSERT), so even a `--dry-run` on the hosted database writes that one row the first time; it writes nothing about any job. The boundary is "more than N days": a job exactly N days old is not moved (spec criterion 1 says "more than N days").

- **Slice 4:** besides the field, the page says how many applications are already past the delay (the sweep's dry-run count, one read, no write to any job), so the operator sees what the next runner pass will do before saving a shorter delay. Console texts are English only, like the rest of the console.

## Order and dependencies
- Slice 1 gives the baseline number the dry run is later compared with, and the scratch copy slice 7 reuses; it needs Docker Desktop running.
- 2 before 3 (the sweep needs the field and the setting); 3 before 4-6 (they read what the sweep writes). 4, 5 and 6 are independent of each other once 2 and 3 are done.
- 7 rehearses 2-6 together on real data before anything reaches the host; 8 is last of the local slices because the runner runs the command only from the PC.
- **The runner and the migration (important):** the PC runs the working tree's code against the hosted database. Once slice 2 is in the tree, any runner step (`run_sources`, `ai sync`, `mail send`) selects the new column and fails on the hosted database until the migration is applied there. So **the owner does not run `pc_runner.ps1` or any command against the hosted database from the new tree before slice 9 shows the migration applied.** (Candidate-view pages on the host keep working: the host runs the old code until the deploy.)
- The sweep runs only from the PC runner (3 to 5 manual runs a week, cycle 001 D6), as the spec allows: no new infrastructure. If the runner is not started for a week, nothing moves that week; the tag shows the day it moved.

## Rollback
- Slices 1-8 change nothing hosted: drop the scratch database (`measure_reads.ps1 -Clean`) and revert or abandon the commits.
- After the push (9): the feature switches off at once with **0 in the console** (nothing moves; tags already set stay and each has its one-tap put-back). The migration is additive (one nullable column, one tiny table) and can stay if the code is reverted; to undo the sweep's effect in bulk, the history lines "auto: no answer after N days" and `auto_rejected_at` identify exactly the rows it moved, and a one-off script (written then, tested on the scratch copy first) puts them back to Applied.
- Slice 10: the owner takes the Neon snapshot before the first real sweep; the dry-run count is the guard (stop if it differs from slice 1 by more than the days that passed).

## Risks
- **A wrong rejection hides a live application:** mitigated by the exemptions, the visible tag, the one-tap put-back, the banner, and the dry run before the first real sweep.
- **First sweep surprise:** on the day it goes live every application older than a month moves at once (Q4, accepted); the count is known beforehand (slices 1 and 10).
- **Shared working tree:** other sessions have uncommitted changes (cycles 013 and 018, tests, `docs/sdlc/README.md`); I stage only my own paths, and stage the README table by editing only my row. Migration number is re-checked before it is written.
- **Insights wording** may need a second look by the owner on a real screen (slice 11).
- **Neon allowances:** the sweep reads only ids and dates, but the owner's pipeline and Insights page views were the heavy readers in cycle 001; criterion 16 is measured in slice 7 and the Insights change adds no history read.
